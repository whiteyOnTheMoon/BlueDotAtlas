## V0.1-Regeln

Alle Endpunkte beginnen mit `/api/v1`, benutzen Node.js/Next.js serverseitig und benötigen **eine aktive Einzeladmin-PostgreSQL-Session** über das bei 025 eingeführte HttpOnly-/SameSite-Strict-Cookie. Anders als die öffentliche Studio-Startseite sind **auch Leseendpunkte privat**. Vor Validierung und Datenbankzugriff wird die Session serverseitig geprüft; der Proxy allein gilt nie als Autorisierung. Antworten setzen `Cache-Control: private, no-store`, `Vary: Cookie` und `X-Content-Type-Options: nosniff`. Kein CORS-Freigabemechanismus für Fremd-Origins.

Alle Sammlungen geben `{ "items": [...], "limit": 20, "offset": 0 }` zurück (Standard: `limit=20`, `offset=0`). **Maximal 50 Einträge pro Seite**, Offset höchstens 10000, stabile Sortierung nach `createdAt DESC, id DESC`. Doppelte oder unbekannte Queryparameter werden mit `400 invalid_input` abgelehnt; Detailrouten erlauben keine Queryparameter. UUIDs müssen kanonischer Form inkl. UUID-Version/Variante entsprechen. Versteckte/gelöschte Datensätze und Einträge unter gelöschten Projekten/Versionen erscheinen weder in Listen noch Details.

| Pfad | Methode | Erlaubte Filter / Funktion |
| --- | --- | --- |
| `/api/v1/projects` | `GET` | `limit`, `offset`, `status` aus [Projektenum](../../packages/core/src/status.ts) |
| `/api/v1/projects` | `POST` | **Nur** `{ "title": "..." }`; 1–160 Zeichen nach Trimmen; atomar Projekt, Revision 1, sieben Wizard-Schritte und Audit; **kein Render** |
| `/api/v1/projects/:id` | `GET` | Projektdetail ohne Soft-Delete-Felder |
| `/api/v1/videos` | `GET` | `limit`, `offset`, `status`, `projectId` |
| `/api/v1/videos/:id` | `GET` | Videometadaten (kein Publish- oder Content-Download) |
| `/api/v1/jobs` | `GET` | `limit`, `offset`, `status`, `projectVersionId` |
| `/api/v1/jobs/:id` | `GET` | Jobstatus, Fortschritt, Versuchszahl, Fehler**code**; **kein** Manifest und keine Worker-Steuerung |
| `/api/v1/media` | `GET` | `limit`, `offset`, `kind`, `projectVersionId` |
| `/api/v1/media/:id` | `GET` | Nur Artefakt-ID, Projektversions-ID, Art, Rechteprüfstatus, Zeitstempel. **Keine** internen Speicherkeys, Quell-URLs, Lizenzrohtexte oder Downloads |

Die Status- und Medienart-Werte sind die vorhandenen, fest definierten Enums aus `packages/core/src/status.ts` (keine frei erfundenen Status). Bei Listenfehlern ist der Body unabhängig von Datenbank-IDs/Queries. Die gemeinsame, ohne zusätzliche bezahlte/technische Abhängigkeiten implementierte Runtime-Eingabevalidierung liegt in `packages/core/src/api-v1.ts`. **Kein Zod-Bundle erforderlich**; spätere Vereinheitlichung braucht einen separaten Dependency-/Lockfile-Review.

## Mutation `POST /api/v1/projects`

Nur `Content-Type: application/json` (optionale Charset-Deklaration), maximal **8192 Rohbytes** inklusive Unicode. Unbekannte JSON-Felder, Status-, Snapshot- oder Script-Felder und **alle Queryparameter auf POST** sind verboten. Browser-Request muss passenden `Origin` und `Host` tragen. Erfolgsstatus `201`, `Location: /api/v1/projects/:id`, Body mit ID, Titel, Status `draft`, aktueller Version `1` und Zeitstempeln. Es wird keine Approval-/Render-/Publikationsaktion gestartet.

Beispiel (bereits mit einer gültigen Admin-Browsersession):

```http
POST /api/v1/projects HTTP/1.1
Content-Type: application/json
Origin: https://studio.example.invalid

{"title":"Arctic sea ice"}
```

## Fehlervertrag

Alle Fehler aus v1 haben dieselbe Form (Feld nur bei Eingabefehlern):

```json
{"error":{"code":"invalid_input","message":"Invalid project input","details":{"field":"title"}}}
```

| Status | Code | Bedeutung |
| --- | --- | --- |
| `400` | `invalid_input` | Ungültiger Parameter, UUID, Bodyfeld oder doppelter Query-Key |
| `400` | `invalid_json` | Nicht parsebares JSON oder nicht lesbare UTF-8-Nutzlast |
| `401` | `unauthorized` | Kein, gefälschter, abgelaufener, widerrufener oder nicht konfigurierter Admin-Login |
| `403` | `forbidden_origin` | Schreibrequest von anderem/fehlendem Origin |
| `404` | `not_found` | Datensatz nicht vorhanden, soft-deleted oder über gelöschtes Projekt verborgen |
| `405` | `method_not_allowed` | Nicht implementierte Methode; mit `Allow`-Header |
| `413` | `body_too_large` | Mehr als 8 KiB JSON-Rohbytes |
| `415` | `unsupported_media_type` | Mutation ohne JSON-Medientyp |
| `503` | `service_unavailable` | Auth-/Datenbankdienst vorübergehend unerreichbar |

Ein unerwarteter Serverfehler darf niemals Stacktrace, SQL, Umgebungsvariablen, Provider-Tokens oder Speicherpfade zurückgeben. Fehlende Auth-Konfiguration verweigert Zugriff (fail-closed). Ein DB-Ausfall bei der Sessionprüfung ergibt `503`; eine anonyme Anfrage bleibt `401`. Für andere Auth- und Login-Endpunkte gelten bis zur späteren expliziten Migration die bestehenden `/api/auth/*`-Verträge aus 025.

## Betrieb, Beweise, Abgrenzung

- **Test:** `pnpm test` (Schema-Negativfälle) plus `node scripts/check-api-v1.mjs` **nur** mit synthetischer Testidentität, eigener lokalen PostgreSQL-16-Datenbank `/bda_test`, gebautem Next.js-Produktionsmodus. Das separate serverseitige Package-Subpath `@bluedotatlas/db/api` importiert bewusst **keine** CLI-Migrationen in Next.js-Bundles. Der dedizierte [API-CI-Workflow](../../.github/workflows/api-v1-check.yml) führt die HTTP-Tests, Security-Header, CRUD-Grenzen, Fail-closed, Datenisolation und Session-Revocation aus. Frische und wiederholte Migration sowie Drizzle-Driftcheck eingeschlossen.
- **Migration:** Aufgabe 026 erzeugt **keine neue Datenbankmigration**; 023–025-Migrationen werden erneut auf einer **wegwerfbaren CI-DB** geprüft. In 029 sind eigene Produktiv-Migrations-/Rollback-/Ressourcengates erforderlich.
- **Nicht-Ziele:** Keine freie UI-CRUD-Maske (031), kein Revision-/Draft-Autosave (032), kein Job-Start/Cancel/Retry/Queue-Worker (027), kein externer Medienabruf/Download/Upload (028ff), kein Publish (M12), kein Live-Deploy (029–030), keine Secrets auf GitHub oder neue Providerkosten.
- **UI-/Video-/Medien-Nachweise:** n/a, weil dieser PR keine Browseransicht, Animation oder Drittmedien ändert. Stattdessen ist der produktionsnahe Next.js-HTTP-Test das maßgebliche API-Artefakt.
