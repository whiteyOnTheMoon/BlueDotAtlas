# Roadmap 033 – Ein verbindlicher CI-Gate für alle Pull Requests

**Status:** 033-Implementierung auf `feat/033-ci-required-quality-gate` für [Issue #50](https://github.com/whiteyOnTheMoon/BlueDotAtlas/issues/50). **Noch keine Betreiberabnahme, keine aktive GitHub-Merge-Sperre verifiziert.**

## Architektur und Ist-Lage

Für frühere Aufgaben gibt es zahlreiche differenzierte CI-Prüfungen (022–032, M00/M01), die meist nur bei Änderungen bestimmter Pfade laufen. Das ist als einzelner verpflichtender Merge-Check ungeeignet. Am 19.11.2026 meldete die GitHub-API ausdrücklich: `main.protected=false` und die Repository-Ruleset-Liste `[]`; detaillierte Branch-Protection-API über die bestehende GitHub-Integration lieferte HTTP 403. **Ein roter Workflow verhinderte daher nicht nachweislich den GitHub-Merge.**

Das neue [`required-ci-033.yml`](../../.github/workflows/required-ci-033.yml) bietet einen stabilen GitHub-Actions-Job mit **Status-/Jobname `033 Required CI`**. Er wird bei **allen** Pull Requests ohne `paths`-/`branches`-Filter ausgeführt, zusätzlich für `merge_group` (falls künftig Merge Queue konfiguriert wird), nach einem Push auf `main` sowie bei manuellem `workflow_dispatch`. Checkout speichert keine GitHub-Credentials, der Job benötigt nur `contents: read`. Er verwendet weder `pull_request_target` noch GitHub Secrets, `continue-on-error` oder stillschweigend ignorierte Fehler.

Die verpflichtende Qualitätspipeline führt aus: Node 22, pnpm 11.28.12 mit Frozen Install; eigene CI-Vertrags-/Negativeingabetests; Monorepo-/Core-Unit; ESLint; Prettier; Typecheck; **echter Next.js-/Monorepo-Build ohne `DATABASE_URL`, `BDA_ADMIN_EMAIL` und `BDA_ADMIN_PASSWORD_HASH`**; erst danach PostgreSQL 16 mit eigens synthetischer DB `localhost/bda_test`; Drizzle-Schema/Journal auf Drift prüfen, zwei Migrationsläufe zur Idempotenz, Datenbank-Integration einschließlich 032-Autosave-Konfliktfall und HTTP-Smoke im Produktionsmodus nur mit synthetischem `*.invalid`-Administrator. **Der Build selbst erhält keine echte oder synthetische Admin-/DB-Verbindung**. Auch beim Smoke wird kein echtes Administratorkonto benutzt.

`scripts/check-ci-033.test.mjs` demonstriert bewusst, dass manipulierte Workflow-Regeln abgelehnt werden und dass absichtlich fehlerhaftes TypeScript bzw. falsche Prettier-Formatierung mit Nicht-Null-Exit enden. `scripts/check-ci-033.mjs` prüft den statischen Pflichtcheck-Vertrag. **Das beweist lokale Fehlererkennung, ersetzt aber weder GitHub-Branch-Protection noch eine rote Merge-Probe.**

## Einmalige GitHub-Einrichtung – Repository-Eigentümer

Die verbundene GitHub-App kann bestehende Regeln lesen, aber hat **keinen Ruleset-/Branch-Protection-Schreibzugriff**. Der Repository-Eigentümer muss den nachstehend vorbereiteten Statuscheck daher manuell zum verbindlichen GitHub-Regelwerk hinzufügen. Zur Auswahl sollte der 033-Check mindestens einmal im neuen PR gelaufen sein.

1. Öffne [GitHub – Repository-Einstellungen / Rules](https://github.com/whiteyOnTheMoon/BlueDotAtlas/settings/rules). Falls die mobile GitHub-Ansicht nicht alle Einstellungen anzeigt, wähle im Browser „Desktopwebsite“. Navigiere zu **Settings → Rules → Rulesets** und wähle **New ruleset → New branch ruleset**.
2. Name z. B. **BlueDotAtlas main CI**; **Enforcement status: Active**, nicht Evaluate oder Disabled. Unter **Target branches** nur **Include default branch** wählen (bei aktuellem Repo: `main`).
3. Aktiviere **Require a pull request before merging** und **Require status checks to pass before merging**. Bei erforderlichen Checks **exakt `033 Required CI`** auswählen (Quelle GitHub Actions). Optional „Require branches to be up to date before merging“ aktivieren, bei Verwendung einer Merge Queue gilt der vorhandene `merge_group`-Trigger.
4. **Block force pushes** und **Restrict deletions** aktivieren, Bypass-Liste leer lassen bzw. nicht global ausnehmen, soweit UI und Berechtigungen es erlauben. **Keine künstliche zweite GitHub-Approval verlangen:** Der alleinige Repository-Eigentümer kann seinen eigenen PR nicht als unabhängiger zweiter Reviewer freigeben; die verpflichtende **Betreiberabnahme im Projektchat (DEC-036)** bleibt bestehen.
5. Ruleset speichern, Status **Active** und gewählten Pflichtcheck im GitHub-UI kontrollieren. Danach GitHub erneut prüfen: `main.protected=true` und – soweit die GitHub-Verbindung Daten lesen kann – aktive Rule mit `required_status_checks` für `033 Required CI`. Ein grüner Action-Run **ohne** aktiven Ruleset-Eintrag zählt nicht als tatsächliche Sperre.
6. Die strenge Abnahme verlangt eine **negative Merge-Probe**: Ein neuer **wegwerfbarer** GitHub-Testbranch/-PR (nur synthetischer fehlerhafter Quelltext, keine Secrets) muss einen roten `033 Required CI`-Job liefern, und GitHub muss im PR **Merge blockiert** anzeigen. Test-PR danach schließen, **nicht mergen**. Dies ist auf GitHub, **nicht** durch einen zweiten VPS-Checkout oder Docker-Stack, durchzuführen.

Alternative, wenn „Rulesets“ nicht verfügbar: **Settings → Branches → Add branch protection rule** für `main`; „Require a pull request“ und „Require status checks to pass before merging“ mit `033 Required CI` und Sperren für Force-Push/Deletion einrichten. Ebenfalls echte rote Merge-Probe prüfen. Offizielle [GitHub-Anleitung zu Rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository) und [Required-Checks-Erklärung](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
